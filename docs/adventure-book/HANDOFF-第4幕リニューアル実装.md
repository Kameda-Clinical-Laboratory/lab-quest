# 第4幕(調査)リニューアル + 冒険の書 — 実装引き継ぎ資料

別チャット(実装フェーズ)に持ち込むための、これまでの検討結果のまとめ。この資料だけで実装に着手できることを目標にしている。

> **2026-08追記(結論の一部を撤回):** §3のフラグワードシステムは、4-A溶血パイロットへの実装・実機プレイの結果、**謎解きの核ではなかった**と判明した。当時は調査カードの中身が「暗記リスト選択」の単調な1パターンだったため、cipher型の文字集め・並べ替えを別のパズル要素として足す方針を取ったが、その後カードの中身自体を「対立仮説の消去」に作り直したところ(`シリーズ作成マニュアル.md` §3.5)、謎解きの手応えはそちらで完結し、フラグワードの並べ替えは「意味のない追加操作」でしかないとプレイして分かった。4-A溶血は`board`型に差し戻し済み。**今後のシリーズはcipher/flagWordを使わず、まず③.5の原則でboard型のまま作ること。** 以下はその判断に至るまでの検討記録として残す。

## 1. 調査タイプ(puzzleType)MVP — 4種

既存の投查(purpose/howTo/choices形式)は `puzzleType: 'board'` として後方互換で扱う。新規追加は以下3種。

| コード | 名称 | 概要 | データの追加要件 |
|---|---|---|---|
| `board` | 証拠ボード型(既存の後継) | 候補カードを見て、該当するものに紐をつなぐ演出。ロジックは既存のchoices(correct配列)のまま、見た目だけ変える | なし(既存choicesを流用) |
| `cipher` | 暗号解錠型(→フラグワード方式に更新、詳細は§3) | 正解すると「文字の欠片」を1つ入手。ユニット内の欠片を後で並べ替えて合言葉を完成させる | 各カードに`fragmentChar`(付与される文字)を追加。ユニット単位で正解の並び順(`flagWord`)を持つ新規フィールドが必要 |
| `order` | 並べ替え型 | 手順・時系列のカードを正しい順に並べる | `steps: string[]`(正しい順序で定義) |
| `match` | 結線マッチング型 | 左列(略語・症状等)と右列(正式名称・原因等)を線で結ぶ | `pairs: {left: string, right: string}[]` |

**D(統合パズル)は独立ビートとしては不採用**。理由: `判断`/`報告`(既存の`resolve`型、`requiredClueIds`で手がかりをロック)とほぼ同じ質問を重複させるだけになるため。ただし「集めた手がかりを組み合わせる快感」自体は§3のフラグワード組み立て画面で別の形で実現している。

## 3. フラグワードシステム(謎解きの核)

ゲームブックの「フラグワードシステム」(数字ではなく意味のある単語でフラグを管理する技法)を参考にした設計。

**流れ:**
1. 調査カード(`cipher`型)に正解すると、`clueKey`と一緒に「文字の欠片」を1文字入手する
2. ユニット内の該当カードをすべて終えると、複数の文字欠片が手元に集まる
3. 判断ビートに進む前に、集めた欠片を並べ替えて言葉を完成させる画面を挟む(アナグラム式UI、新規実装が必要)
4. 完成した言葉は「冒険の書」巻末索引でも同じ語を引けるようにしておく(答え合わせ・確認の役割)

**改版耐性のための設計原則:**
- 冒険の書側の参照(`howTo`)は**ページ番号ではなく項目コード**(`4-A-c` のような小項目コード、`①②③④` のコラム番号)を使う。ページ番号は版が変わるたびにずれるが、項目コードは本文の並び順を大きく組み替えない限り変わらない
- 巻末索引(②索引方式)を補助として用意する

**具体例(4-A溶血、あくまでイメージ):** 調査カード「偽高値になる項目」正解→「み」、「偽低値になる項目」正解→「わ」、3枚目があれば「け」→ 並べ替えて「みわけ」(見分け)完成。**実際の文字割り当ては各シリーズ制作時に個別に決める。**

## 6. 冒険の書(印刷配布用参考資料)

### 目的
1. 実習生ごとに教科書が違って答えの表記がぶれる問題を解消(統一の一次資料を提供)
2. 調査カード(特にcipher型)・観察系の謎解きネタの供給源にする

### 制作方針
- 単位: シリーズごとに付録として作る(骨子案の目次:大項目23/中項目67/小項目254がベース)
- 形式: Word(PowerPointも可)、A4印刷前提。表は作り込む。図・写真は差し込み枠だけ用意し、実物はスタッフ(ユーザー本人)が挿入
- 元ネタ:
  - `docs/materials/`(スキャン教科書31冊、522MB)
  - `docs/national exam/`(国試第52〜62回、ローカルにファイルあり)
  - 厚労省サイトから追加取得した第63〜72回(現行の令和7年版出題基準は第71回・2025年〜適用。出題基準PDF: `https://www.mhlw.go.jp/content/10800000/001080955.pdf`)
  - 上記で不足する場合は信頼できるWeb情報で補う
- 著作権配慮: 原文の丸写しはせず、事実・数値・表を独自の文章で要約する
- 表の数値データには**出典を表の直下に明記**する
- 各章末に国試型の設問は**入れない**(アプリの発展ドリルで解かせる方針。解説はそのまま流用可、`docs/adventure-book/notes/`配下に退避しておく運用)
- 施設差(◆)がある内容は、自施設のデータ・手順を優先する旨を明記する

### 品質チェック
- 内容が固まったら`clinical-content-reviewer`で臨床的正確性を検証する(CLAUDE.mdの既存ルールに準拠、通常フローはcontent/series/*.mjsが対象だがこの冒険の書にも同様に適用している)

## 8. このWindows環境でのWord生成に関する技術メモ

- リポジトリは `"type": "module"` (ESM) なので、`docx`パッケージを使うNode生成スクリプトは **`.cjs`拡張子**にすること(`.js`だと`require`が使えずエラーになる)
- `docx` npmパッケージはこの環境にプリインストールされていない。生成スクリプトのディレクトリで `npm install docx --no-save` が必要
- **この環境にはLibreOffice・pandocが無い**ため、`skills/docx`付属の`soffice.py`によるdocx→PDF変換・視覚確認ができない。代わりに以下で内容チェックする:
  ```python
  import docx
  d = docx.Document('xxx.docx')
  # 段落・表を順に走査してプレーンテキスト化 → clinical-content-reviewer等に読ませる
  ```
  (`python-docx`はインストール済み。実行ファイルは `C:\Users\うめ\AppData\Local\Python\bin\python.exe` を使うこと。`python3`/`python`エイリアスはWindows Storeスタブで動かない)
- 視覚的なレイアウト確認は、生成したdocxをユーザーに送ってユーザーの実機Wordで見てもらう運用にしている(このリポジトリ環境では代替できない)
- スキャンPDF(`docs/materials/`配下)は`pdftotext`/`pypdf`/`pymupdf`のテキスト抽出がいずれも文字化けする。**PyMuPDFでページをPNGレンダリングしてReadツールで目視する**方法のみが機能する。国試の一部の回(60〜70回)はテキストレイヤーが生きていて`pymupdf`の`get_text()`が使えることもあるので、まず試してから判断するとよい
