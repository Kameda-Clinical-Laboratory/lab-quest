# 生化学免疫ラボクエスト — シリーズ作成マニュアル

この文書は、シリーズ（学習パッケージ）を **別の作成者** が同じ型で作るための手順書です。  
アプリ実装の詳細ではなく、「学習の流れ・中身の書き方・チェックリスト」を定めます。

---

## 1. この教材で目指すもの

- 目的は娯楽ではなく、**忙しい指導スタッフの代理**として、臨床寄りの学びを進めること
- 午前の自習（最大おおよそ4時間）で使い、午後は現場実習
- **音は出さない**（院内）。フィードバックは文章・色・進捗表示のみ
- ゲーム寄せは **目盛り2** まで
  - やる: 依頼・Dr./Ns.との会話、手がかり／図鑑、謎解き感のある調査
  - やらない: 仮想マップ歩行、ポケモン型探索、村RPG化、ランキング、音響演出

---

## 2. いちシリーズの全体像

1つのシリーズ ＝ 1つのまとまった学習テーマ（例: 基礎知識、溶血、採血管）。

```text
シリーズ
 ├─ ユニット1
 ├─ ユニット2
 ├─ ユニット3 …
 └─ （任意）シリーズ末の総合症例
```

- **必須シリーズ**と**任意シリーズ**がある（運用カレンダーで割当）
- 手技チェックが必要なシリーズは、別途「手順シミュ」をクリア必須にする（既存方針）
- 最終CBTは、クリア済みシリーズの問題プールから構成する（シリーズ作成時は発展問題をCBT転用できる形で書く）

---

## 3. ユニットの基本フロー（最重要）

各ユニットは、次の **固定順** で作る(2026-08、幕構成リニューアル後の正本。実装上のbeat配列は下記7幕)。

```text
第1幕 会話（症例が開く。beat.titleは自由記載）
 → 第2幕 クエスト発生（unit.title/requestLineをそのまま表示。編集不可）
 → 第3幕 講義（解決に必要な最小知識）
 → 第4幕 調査（その症例を解くための手がかり集め。1〜複数のinvestigateビートを1つの調査ハブにまとめる）
 → 第5幕 判断（1問目のresolve。手がかりを使った初動判断）
 → 第6幕 報告（2問目のresolve。判断を踏まえた最終的な報告方針。無ければ省略可）
 → 第7幕 発展（定着・一般化。国試形式の設問）
```

**幕タイトルの付け方**: 第2〜7幕は上記の固定名を`beat.title`にそのまま設定する(会話だけ自由記載)。特に **resolveビートが2つ以上あるユニットでは、1つ目に`title: '判断'`、2つ目に`title: '報告'`を必ず設定すること**(未設定だと種別ラベル「解決」がどちらにも表示され、サイドバー上で見分けがつかなくなる。既存の`bio-hemolysis-u1`もこの命名で統一済み)。調査ハブの「判断へ進む」ボタン文言もこの固定名に合わせてある。

### 設計の核

- **調査は独立した座学ではない。症例解決のために行う。**
- 最初の会話で「何に困っているか／何を決める必要があるか」を見せる
- 学習者は、講義と調査で手がかりを揃えてから、同じ症例に戻って解決する
- 発展問題は「その症例が解けたあと」に、国試・現場で使える形へ一般化する

### やってはいけない流れ

- 長い講義 → 確認問題の繰り返しだけで終わる
- 調査だけして症例に戻らない
- いきなり正解解説から入る（症例が開いていない）
- 調査なしで症例解決できる（必須手がかりを置かない）

## 4. 各ステップの書き方

### ① 会話（症例オープン）

**役割:** 依頼・困りごとを提示し、学習者に「解決すべき問い」を持たせる。

| 項目 | 内容 |
|------|------|
| 話者 | Dr. または Ns.（必要なら検査技師・他職種） |
| 場面 | 検査室・病棟・報告場面など、現実に起きうる状況 |
| 出し方 | 短い会話（目安 4〜8 吹き出し） |
| 終わり方 | 「確認してきてほしい」「一緒に判断したい」など、**調査への動機**で閉じる |
| この時点の解答 | 本正解は求めない（軽い意思表示の選択は可） |

**書くこと**

- 患者・検体は匿名化（実在個人が特定できない）
- 施設固有の電話番号・氏名は出さない（「施設の連絡手順に従う」と書く）
- 学習目標を会話の裏に隠す（例: 本当は「パニック値対応」を学ばせたい）

**依頼票に残す一文（必須）**

- 例: 「溶血疑いのK高値を、報告前にどう扱うか決める」

---

### ② 講義

**役割:** 症例解決に必要な知識だけを短く渡す。

| 項目 | 目安 |
|------|------|
| 分量 | 画面1〜2枚、おおよそ 200〜500 字 |
| トーン | 指導メモ／マニュアル。教科書の丸写しにしない |
| 含める | 用語の意味、現場での見方、次の調査で何を確かめるかの予告 |
| 含めない | そのユニットで使わない枝葉、長い歴史・原理の羅列 |

講義の末尾に、調査への橋渡しを1文入れる。

- 例: 「次に、教科書で『溶血の影響を受けやすい項目』を確認してこよう。」

---

### ③ 調査（手がかり集め）

**役割:** 現実世界（教科書・資料・検査室観察）から、症例解決に必要な手がかりを取る。

アプリは地図探索をしない。アプリがやることは次だけ。

1. **何を調べ／観察するか**を指示する  
2. **持ち帰って入力する答え**を受け取る  
3. 正解なら **手がかり／図鑑** に登録する  

#### 調査の種類

| 種類 | 例 | 必須／任意 |
|------|-----|------------|
| 教科書・配布資料で調べる | 国試頻出キーワード、定義、影響項目 | 原則 **必須**（症例の鍵） |
| 施設資料で確認する | パニック値手順、報告ルート | テーマにより必須 |
| 検査室の観察 | 受付→遠心の流れ、掲示物 | **短時間・任意が多い**（必須にする場合は理由を明記） |

#### 観察・実地のマナー（カードに必ず書く）

- ルーチンの邪魔をしない
- 不要に声をかけない（緊急時・決められた相談先以外）
- 触ってよい物／見てよい範囲だけ
- 目安時間（例: 5分以内）

#### 1つの調査カードに書く項目

1. **この症例のために確かめること**（目的）  
2. **調べ方**（教科書の章の目安、資料名、観察場所の目安）  
3. **入力してほしい答え**（キーワード、番号、短い語句）  
4. **マナー**（観察のとき）  
5. **正解時に得られる手がかり名**（図鑑に載る名前）

作成者メモ（学習者には出さない）として、正答・許容ゆれ・解説を別欄に残す。

---

### ④ 症例解決

**役割:** ①の会話に戻り、③で得た手がかりを使って判断する。

| 項目 | 内容 |
|------|------|
| 形式 | Dr./Ns.との会話＋分岐選択（1〜3問程度） |
| 前提 | **必須手がかりが揃っていないと進めない** |
| 正解 | 臨床的に妥当な行動・判断（施設差がある場合は「自施設手順を優先」と書く） |
| 不正解 | 減点で終わらせず、なぜ違うか・次に何を見るかを返す |

**手がかりの使い方（作成時に決める）**

- 解決画面に「所持手がかり」を表示する  
- または、選択肢の根拠を手がかり名で参照できるようにする  

解決の締めは、依頼が一段落した実感が出るようにする（報告方針が決まった、再検の要否が分かった、など）。

---

### ⑤ 発展問題

**役割:** その症例の学びを、国試・他場面でも使える知識に一般化する。

次の形式から **2種類以上** を混ぜる（同じ四肢択一の連打にしない）。

| 番号 | 形式 | 向く内容 |
|------|------|----------|
| 1 | データ表・報告文を読んで選ぶ | 結果解釈、報告文の妥当性 |
| 2 | 分岐選択（短い状況判断） | 対応の優先順位 |
| 3 | 並べ替え／対応づけ | 検体の流れ、因果、部門連携 |
| 4 | 誤り探し | 性状・手順・報告のおかしい点 |

目安: 発展問題は **3〜6問**。解説は必ず付ける（事後に読める）。  
最終CBTに載せたい問題は、解説・出典シリーズが分かる形で残す。

---

## 5. キャラクターの使い方

最低限、次をシリーズ内で一貫させる。

| 役 | 役割 |
|----|------|
| 実習生（学習者） | 調査し、判断する主人公 |
| Dr. | 臨床側の問い・報告の受け手 |
| Ns. | 病棟・検体・優先の現場感 |
| （任意）先輩技師 | 検査室側の手順・安全 |

- 人格は簡潔でよい（口調を固定する）
- 雑談イベントを増やしすぎない（学習密度を落とす）
- キャラが間違った医療行為を「正解」にしない

## 6. 1ユニット分の原稿テンプレート

作成者は、ユニットごとに次を埋める。

```text
【シリーズID / ユニット番号 / タイトル】
【学習目標】（1〜3個。行動や判断で書く）
【依頼票の一文】（未解決の問い）

■ ① 会話（症例オープン）
- 話者:
- 場面:
- 会話原稿:
- 学習者に残る問い:

■ ② 講義
- 本文:
- 調査への橋渡し文:

■ ③ 調査（症例のための手がかり）
調査A（必須）
- 目的（症例との関係）:
- 調べ方（教科書/資料/観察）:
- 入力させたい答え:
- 正答・許容ゆれ:
- 得られる手がかり名:
- マナー（観察時）:

調査B（任意/必須）
- （同様）

■ ④ 症例解決
- 必要手がかり一覧:

- 問1（形式番号・問題・正答・解説）:

【所要時間目安】分
【注意】施設差・触れてはいけない実在情報
```

## 7. シリーズ全体の組み立て方

1. シリーズの到達目標を1文で書く  
2. ユニットを 2〜4 本に分割する（1ユニット＝1つの症例ストーリー）  
3. 各ユニットを「会話→講義→調査→解決→発展」で書く  
4. ユニット間で図鑑キーワードが再利用されると望ましい（学びの連続）  
5. 手技ありシリーズは、手順シミュの位置を明記する（通常は症例解決後〜シリーズ末）  
6. 匿名化・教材化チェックを通す  

### 分量の目安（午前自習）

| 要素 | 目安 |
|------|------|
| 1ユニット | 20〜40分 |
| 1必須シリーズ | ユニット2〜4本（合計おおよそ1〜2.5時間） |
| 1日の割当 | シリーズ0〜N本（0本＝見学などアプリなし日） |

作成時点で「長すぎる講義」になっていないか、通読時間で確認する。

## 8. 品質チェックリスト（提出前）

### 流れ

- [ ] 会話で症例（問い）が先に開いている  
- [ ] 講義が短く、その症例に必要十分な内容だけである  
- [ ] 調査が「症例解決の手がかり集め」になっている  
- [ ] 必須手がかりなしでは解決できない設計である  
- [ ] 解決のあと発展問題がある  
- [ ] 発展に形式1〜4のうち2種類以上ある  

### 安全・運用

- [ ] 音前提の指示がない  
- [ ] 観察がある場合、邪魔しない・短時間・声かけルールが書いてある  
- [ ] 個人情報・実在患者が特定できない  
- [ ] 施設差がある判断は「自施設手順優先」と書いてある  
- [ ] 診断行為を実習生にさせていない  

### 面白さ（目盛り2の範囲）

- [ ] 依頼票の一文で「何を解決するか」が分かる  
- [ ] 手がかりに名前があり、解決で使った実感がある  
- [ ] 同じ四肢択一の連打だけで終わっていない

## 9. 良い例 / 弱い例

### 良い例（ユニットの骨）

1. Ns.「このK、報告していい？朝から溶血っぽい検体で止まってる」→ 問いが開く  
2. 講義「溶血で動きやすい項目と、報告前確認」  
3. 調査「教科書で溶血の影響項目を調べ、キーワード入力 → 手がかり『溶血影響』入手」  
4. 解決「手がかりを踏まえ、再検・コメント・相談のどれか」  
5. 発展「データ表読み＋誤り探し」

### 弱い例

- 講義3枚 → 確認問題3問 → 終了（症例が開いていない）  
- 「検査室を自由に歩いて何か見つけて」だけ（目的が症例に紐づかない）  
- 調査せずに正解肢が当てられる（調査が儀式になっている）

## 10. 提出物（作成者 → 実装・編集担当）

シリーズごと、次をセットで渡す。

1. シリーズ概要（タイトル、必須/任意、手技の有無、到達目標）  
2. ユニット原稿（本マニュアルのテンプレート通り）  
3. 図鑑キーワード一覧（名前・定義1文・登場ユニット）  
4. キャラ口調メモ（任意だが推奨）  
5. CBT転用候補リスト  
6. チェックリスト記入済みコピー  

疑問点は「学習目標」と「症例の問い」を先に合意してから本文を書くと手戻りが少ない。

## 11. 用語の対応（現場 ↔ アプリ）

| 作成者・現場の言葉 | アプリ上のイメージ |
|--------------------|--------------------|
| シリーズ | クエスト／ステージ |
| ユニット | 1件の依頼 |
| 会話で開く問い | 依頼票の一文 |
| 調査結果 | 手がかり／図鑑 |
| 症例解決 | 依頼の決着 |
| 発展問題 | 追加訓練／ボス手前の演習 |

言い回しはシリーズ内で統一する（「ステージ」「クエスト」を混在させすぎない）。

## 12. 実装スキーマ対応表（編集担当向け）

原稿をアプリに落とすときのフィールド名。正本コード: `src/mocks/learning.ts` / 例: `src/mocks/bioBasicsUnits.ts`。

### LearningUnit

| フィールド | 必須 | 意味 |
|------------|------|------|
| id | yes | ユニットID（例: bio-basics-u1） |
| title | yes | ユニット名 |
| requestLine | yes | 依頼票に常時表示する一文 |
| beats | yes | Beat の配列（会話→講義→調査→解決→発展の順） |

### ClueDef（図鑑）

| フィールド | 必須 | 意味 |
|------------|------|------|
| id | yes | 手がかりID（investigate.clueId / resolve.requiredClueIds と一致） |
| name | yes | 表示名 |
| summary | yes | 1文の定義 |

### Beat.type

| type | 役割 | 主なフィールド |
|------|------|----------------|
| dialogue | 症例オープン | lines[{ speaker, text }], xp? |
| lecture | 短い講義 | body, bridge?, xp? |
| investigate | 調査（手がかり集め） | mode: textbook\\|doc\\|observe, purpose, howTo, choices[{ label, correct }]（複数正解可・チェックボックス選択式。2026-08に自由入力inputPrompt/acceptedAnswersから刷新）, clueId, required, manners?, demoHint?, xp? |
| resolve | 症例解決（1幕=1問。2026-08に複数ステップ内包から刷新） | requiredClueIds[], prompt, choices[{ label, correct, feedback }], xp? |
| drill | 発展（MVPは mcq） | questions[{ id, format:'mcq', prompt, choices[{ label, correct }]（複数正解可・チェックボックス選択式。2026-08にcorrectIndexから刷新）, explanation }], xp? |

### ゲート・救済（実装済み）

- resolve は requiredClueIds がすべて所持手がかりに含まれるまでロック
- investigate.required=false はスキップ可（ボーナス放棄）
- キーワード不一致: 3回で demoHint、5回で正答開示＋手がかり付与
- 解決・発展の不正解は減点なし・再選択可

### 旧シリーズ互換

- Stage.units がある → 新UI
- 無い → 従来の chapters + case + procedure
